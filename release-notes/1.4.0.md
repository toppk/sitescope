# sitescope 1.4.0

Devices and services (`docs/roadmap.md`). Existing deployments see no
change until they configure the new options: the production config builds
the same checks as 1.3.0, with the same ids, names, areas, timing and
probes.

## Features

- Units and timers: a host's `units` lists systemd units that must be
  active (`host.HOST.unit.NAME`). A timer must also be scheduled, its last
  run must have succeeded, and it must not be overdue or older than
  `maxAge`. `user: true` asks the agent user's own manager, and `severity`
  is `crit` or `warn`. The hub sends the list with each poll, so it is set
  only in the hub's config.
- Hosts not on NixOS get `host.HOST.reboot` (a newer kernel installed than
  running) and `host.HOST.updates` (days since the package database
  changed: `updatesAge {30, 90}`).
- Devices, in a new `devices` area: `ping` (unprivileged ICMP, loss and RTT
  thresholds), `tcp` (a port accepts connections) and `ipp` (printer state
  and every supply's level over IPP). `seenWithin` keeps a device that
  sleeps ok while it answered within the window.
- HTTP targets take `ca` (a private CA or a device's self-signed
  certificate), `body` (text the response must contain) and `redirect`
  (where it must redirect).
- ntfy: `alerts.ntfy` pushes crit changes (or warn with `min: "warn"`) and
  their recoveries to the topic in `SITESCOPE_NTFY_URL`. A push carries
  counts, or check names with `details: true`.
- `sitescope verify -url …` reads a hub's `/healthz` and `/status.json` and
  checks the version, vault state, overall status and counts. `-ca` trusts a
  private CA.
- CI runs the tests, both builds, a version check of each, and
  `nix flake check` on every push.

## Bug fixes

- When one notifier failed, every notifier got the message again on the
  next pass. Now only the failed one does.

## Breaking changes

- None. The agent report gains `services`, `kernel` and `packages`. Older
  hubs ignore them, and a 1.3.0 agent answers a 1.4.0 hub as before. The
  new checks for it report unknown and say it needs 1.4.0.

## Upgrade notes

- Pin the release commit and redeploy; then `sitescope unlock` on the hub host.
- Rollback: two-way. No state changes. 1.3.0 accepts a config that uses
  the new options but ignores them, so an HTTP target with `redirect` goes
  back to expecting 200.
- Verify: `sitescope verify -url <hub> -version 1.4.0+<rev>`; the check
  count is unchanged, and the next alert or digest arrives by email.
- ntfy needs its own handoff: the topic URL in the environment file, then
  `alerts.ntfy.enabled`.
